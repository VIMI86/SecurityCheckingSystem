# SentinelAI

Учебная микросервисная платформа, которая координирует специализированных ИИ-агентов для анализа событий информационной безопасности и подготовки предложений по реагированию. Действия агентов не выполняются сами по себе: Policy Service возвращает `ALLOW`, `DENY` или `REQUIRE_APPROVAL`.

Это промежуточный учебный MVP. Сначала закрываются обязательные требования курса, затем добавляется сценарий с агентами.

## Проблема

События приходят из сетевых IDS, системных журналов и сервисов. Первичный разбор занимает время. LLM ускоряет разбор и черновик рекомендаций, но прямой доступ агента к инфраструктуре опасен. Нужны оркестрация, проверка политик, аудит и ограничение сетевых связей.

## Цель

Принять задачу анализа события безопасности, обработать её одним или несколькими агентами, применить централизованную политику и сохранить результат вместе с аудитом. Платформа при этом закрывает пять этапов курса: описание, микросервисы, данные и брокер, сеть и firewall, отказоустойчивость.

## Задачи

1. Зафиксировать описание, схему и обоснование стека.
2. Поднять минимальные сервисы одной командой Docker Compose.
3. Показать CRUD в PostgreSQL, чтение и запись в Redis, публикацию и потребление в RabbitMQ.
4. Разделить сети и проверить разрешённый трафик, запрещённый трафик и отказ при блокировке нужного правила.
5. Показать учебный failover PostgreSQL и RabbitMQ, backup и restore, и обосновать целевые SLO, RPO, RTO, MTTR, MTBF.
6. Подключить Analyst Agent и Security Agent через адаптер LLM. Опасные операции только предлагаются и проходят политику.

## Аудитория

Учебная лаборатория по информационной безопасности и микросервисам. Домашняя лаборатория для экспериментов с логами и контейнерами. Демонстрация на стыке backend, DevOps, cybersecurity и AI.

## Сценарий использования

Клиент отправляет `POST /tasks` с типом события и исходными данными. API создаёт задачу и публикует сообщение. Orchestrator запускает Analyst Agent, затем Security Agent. Policy Service проверяет предложенное действие. Клиент опрашивает `GET /tasks/{task_id}` до завершения. Журнал решений хранится в аудите.

## Границы MVP

Входит:

- Backend на FastAPI: API Gateway, Orchestrator, агенты, Policy, Audit.
- Два агента: Analyst и Security. Третий агент — расширение.
- Адаптер LLM с режимами `mock` и `ollama`.
- PostgreSQL, Redis, RabbitMQ, Docker Compose.
- Сетевые сегменты и документированный firewall.
- Учебная репликация и переключение PostgreSQL и брокера, backup и restore.
- Проверки ключевых сценариев и инструкция демонстрации.

Остаётся за рамками первого MVP:

- Kubernetes, service mesh и промышленный кластер.
- Отдельный frontend. Достаточно OpenAPI, curl и статуса задачи.
- Выполнение опасных команд агентами на хосте.
- Десятки агентов, сложный RAG и обучение собственной модели.
- Промышленный SLA. Показатели обслуживания — учебные целевые значения.

## Требования

Функциональные:

- Принять событие, выдать `task_id`, отдать статус и результат.
- Прогнать задачу через очередь и воркер.
- Сохранить задачу, результат агента, решение политики и событие аудита.
- Вернуть `ALLOW`, `DENY` или `REQUIRE_APPROVAL`. Неизвестное действие запрещается.
- До подтверждения чувствительное действие не выполняется. В учебном MVP опасные операции только симулируются.
- Кэшировать статус задачи с TTL и сбрасывать кэш при изменении.
- Работать с фиксированными ответами mock-провайдера, если Ollama недоступна.

Нефункциональные:

- Один разработчик поднимает стек на Ubuntu командой `docker compose up --build`.
- Секреты живут в окружении, не в git.
- У каждого сервиса есть health endpoint.
- В логах есть `task_id`, секреты в логи не пишутся.
- Порты PostgreSQL, Redis и RabbitMQ наружу не публикуются без необходимости.
- Firewall на ноутбуке не перекрывает SSH и доступ к Ollama на homelab.
- Агенты не получают shell и Docker socket.

## Где что работает

Весь учебный стек этапов 2–5 работает на ноутбуке. Homelab отдаёт только модель Ollama по HTTP в локальной сети. Подробности — в [docs/deployment.md](docs/deployment.md).

## Запуск

```bash
docker compose up --build -d
docker compose ps
curl -fsS http://127.0.0.1:8000/ready
curl -fsS http://127.0.0.1:8001/ready
curl -fsS http://127.0.0.1:8002/health
```

`/` отвечает hello. `/health` показывает, что процесс жив. `/ready` проверяет зависимости сервиса. Пароль учебной базы и брокера по умолчанию `sentinel`. Свой локальный файл создаётся копией `.env.example` в `.env` и в git не входит.

Страница задач открывается на `http://127.0.0.1:8000/ui`. Корень API по-прежнему отвечает JSON `hello`, его использует проверка этапа 2.

Порты API, Orchestrator и Agent опубликованы только на `127.0.0.1` (8000, 8001, 8002). PostgreSQL и Redis наружу не публикуются. Интерфейс RabbitMQ доступен на `http://127.0.0.1:15672`. Контейнеры разнесены по сетям `sentinelai_edge`, `sentinelai_app`, `sentinelai_data` и `sentinelai_broker`. Правила фильтра и откат описаны в [docs/network-security.md](docs/network-security.md).

Остановить стек: `docker compose down`. Том PostgreSQL при этом сохраняется.

### Задача, кэш и очередь

`sql/schema.sql` копируется в образ API и применяется при его старте. Так схема ставится и на уже существующий том. На этом диске bind-mount файла в контейнер превращается в пустой каталог, поэтому схема не монтируется с хоста.

```bash
curl -fsS -X POST http://127.0.0.1:8000/tasks \
  -H 'content-type: application/json' \
  -d '{"event_type":"ids_alert","payload":{"src":"10.0.0.8","msg":"ET SCAN"}}'
curl -fsS http://127.0.0.1:8000/tasks/TASK_ID
curl -fsS http://127.0.0.1:8000/tasks/TASK_ID
curl -fsS -X PATCH http://127.0.0.1:8000/tasks/TASK_ID \
  -H 'content-type: application/json' \
  -d '{"payload":{"src":"10.0.0.9","msg":"updated"}}'
curl -fsS -X DELETE http://127.0.0.1:8000/tasks/TASK_ID
```

Первый `GET` после обработки отвечает `"cache":"miss"` и заполняет Redis на 30 секунд. Следующий `GET` отвечает `"cache":"hit"`. `PATCH` и завершение воркера удаляют ключ. Orchestrator подтверждает сообщение в RabbitMQ только после записи результата. Повторная доставка проверяется телом `{"simulate_error": true}`: первый раз сообщение возвращается в очередь, со второй попытки задача завершается.

Интеграционные тесты ходят в уже запущенный API:

```bash
python3 -m pip install --target .pydeps -r requirements-dev.txt
PYTHONPATH=.pydeps python3 -m pytest -q tests/test_stage3.py
```

## Дальше

Analyst и Security работают в контейнере агента. Policy в оркестраторе решает `ALLOW`, `DENY` или `REQUIRE_APPROVAL` по таблице `policies`. Приложения смотрят на `postgres-standby`: исходный primary остановлен, его том сохранён.
