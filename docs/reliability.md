# Надёжность и восстановление

Учебный контур. Цифры ниже разделены на целевые и на то, что реально наблюдалось в одном прогоне на ноутбуке. Это не промышленная гарантия.

## PostgreSQL

Два экземпляра одной и той же сборки `deploy/postgres`:

- `postgres` — исходный primary. Данные лежат в прежнем томе `postgres_data`, он не удалялся.
- `postgres-standby` — реплика. При первом запуске снимает базовую копию с primary через `pg_basebackup` и дальше читает WAL. Пока реплика не продвинута, она только для чтения.
- Репликация асинхронная. Транзакция, которую standby ещё не получил, при падении primary теряется. Отдельного автоматического VIP нет.

Переключение ручное: `./scripts/postgres-failover.sh`.

1. Пишет маркер на primary и ждёт, пока он появится на standby.
2. Останавливает primary. Том не трогает.
3. Выполняет `pg_promote()` на standby.
4. Записывает в `.env` строку `POSTGRES_HOST=postgres-standby` и пересоздаёт API и Orchestrator.
5. Заново применяет firewall: у новых контейнеров другие адреса, старые правила их не пустят.

Обратная репликация со старого primary не строится. Чтобы вернуть пару, нужен новый `pg_basebackup`, а не запуск старого контейнера как есть.

## Backup и restore

`./scripts/postgres-backup.sh` делает `pg_dump -Fc` в `backups/sentinel.dump` и поднимает отдельный экземпляр `postgres-restore` (профиль Compose `restore`). Восстановление идёт в его собственный том. Основной том не перезаписывается.

## RabbitMQ

Три узла: `rabbitmq`, `rabbitmq-2`, `rabbitmq-3`. Общий Erlang cookie, очередь `sentinel.tasks` типа quorum. Клиенты подключены к первому узлу, панель остаётся на `127.0.0.1:15672`.

Кворум из трёх узлов переживает остановку одного. Остановка двух узлов оставляет меньше половины, очередь перестаёт принимать запись. Скрипт `./scripts/rabbitmq-cluster.sh` собирает кластер, останавливает только третий узел, проводит задачу и запускает узел снова.

## Что наблюдалось

- Строка `replica_check` появилась на standby, пока primary ещё работал.
- Дамп занял 8590 байт. В восстановленной базе было 6 задач со статусом `done`. Это состав базы на момент дампа, не обещание на будущее.
- Маркер `failover_marker` был виден на standby до остановки primary и остался после `pg_promote()`. Новая задача `after_failover` дошла до `done` уже через promoted-узел.
- При остановленном `rabbitmq-3` задача `quorum_failover` дошла до `done`. Очередь при этом была `quorum`. Узел после проверки запущен снова.
- Первый замер времени всего скрипта переключения не годится как RTO: API завис на старте, потому что firewall ещё разрешал старый адрес контейнера.
- Чистый прогон сделан уже после того, как правила стояли на актуальных адресах. Секунды ниже включают остановку primary, `pg_promote()`, пересоздание API и повторный `firewall apply` до успешного `/ready`.

## Учебные цели и измерения

| Показатель | Учебная цель | Что измерено в этом прогоне |
| --- | --- | --- |
| RPO | Не больше нескольких секунд уже подтверждённых транзакций. Репликация асинхронная, нулевой потери журнал не обещает. | Маркер был виден на standby до остановки primary и остался после `pg_promote()`. Лаг в миллисекундах не снимался. |
| RTO | Ручное переключение и ответ API укладываются в 2 минуты, если firewall обновлён сразу после новых контейнеров. | Чистый прогон: 13 секунд от остановки primary до успешного `/ready`, уже вместе с обновлением firewall. |
| MTTR | Для одной учебной аварии совпадает с временем этого восстановления. Это не среднее за год. | 13 секунд в этом единственном чистом прогоне. |
| MTBF | Не выводится из одного эксперимента. | Не измерялся. |
| SLO | После ручного переключения `/ready` API снова успешен, а задача проходит до `done`. | `/ready` успешен. Задача `rto_check` после переключения дошла до `done`. |
